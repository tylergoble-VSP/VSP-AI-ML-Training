Pre-work · 20 min · The Keywords

Three words, one test each.

Deterministic

Same input → same output, every time, on your machine and in CI. The output is a function of the input and nothing else.

Anchors: 2 + 2 · a SQL SUM · a build with pinned deps · a sha256. If you can cache it forever, it is this.

Probabilistic

The output is a guess with a stated confidence — and the confidence is an auditable claim, not a decoration.

Anchor: "spam, confidence 0.87" — of the mail it scores near 0.87, about 87 in 100 should really be spam. Go and check.

Stochastic

There is randomness inside the process, so the same input can give different outputs on different runs.

Anchors: retry jitter · load-balancer routing · SGD training · an LLM sampling at temperature > 0.

Probabilistic is about the shape of the answer. Stochastic is about the machinery. A system can be one, both, or neither — and most ML systems are different ones in different places. That is today's whole skill.

Misfile · a flaky test

Deterministic code in a stochastic environment. Nothing samples — you are missing an input (clock, port, thread schedule).

Misfile · a hash

Looks random, is deterministic. 1,000 calls, one digest. Looks random and is random are unrelated properties.

Misfile · an LLM at temperature 0

Near-deterministic in practice, not contractually. Float addition is not associative: batching moves a score by 4.5e-13, and tied candidates flip. Two minutes, then park it.

One model, all three buckets: training is stochastic — 8 retrains move accuracy 0.8 points and one deal's score 4.5 points — inference is deterministic once weights are pinned, and the output is probabilistic. So never answer "is it deterministic?" — ask "which part?"

Segment 2 · Expectation-Setting

Pin it, or don't promise it.

"It varies" is not something a client can buy. "It varies in these ways, within these bounds, and here is what is nailed down" is.

Pinned — so a ticket becomes a replay

  • Temperature — explicit, never a default
  • Model version — a dated snapshot, not a floating alias
  • Prompt + template version — stamped on every logged answer
  • Retrieval config — index snapshot, chunking, top-k, filters
  • Seeds, where the API exposes them — logged with the request id

Cannot promise — say this instead

Byte-identical wording"Identical facts and citations; wording may vary — here is the measured rate."
Sameness after an upgrade"Upgrades are scheduled and we re-run the eval set. You see both numbers."
Sameness after re-indexing"New content changes answers — that is the product working."
100% correctness"≥ N% on a versioned golden set, every answer citable."
Acceptance criteria for a probabilistic system are eval sets and thresholds — never exact-match outputs. The lesson plan's example: "≥ 90% of a 50-question test set judged correct." Good sentence. Next slide does the arithmetic on it.

Segment 2 · The Working Attitude

"All models are wrong,
some are useful."

Usually deployed as a shrug. It is the opposite of a shrug — it is a job description, and it is what you are actually selling.

Understood

You know which kind of wrong: a missed fraud or a false alarm, a wrong fact or a clumsy sentence. Naming the error is half the deliverable.

Bounded

You know how big and how often — a measured rate on a versioned set, not an adjective. "Mostly reliable" is not a bound.

Priced in

The workflow survives the errors, and somebody has decided who eats the cost — a reviewer, a threshold, a human sign-off.

Three sentences, in order: 1. "It samples, so wording varies — facts and citations don't; here is the measured rate." 2. "We pin temperature, model version, prompt version and the index snapshot, and log the request id — any answer can be replayed." 3. "We contract on a number: ≥ 90% on a versioned golden set, re-run every release — let's build that set from your questions."
